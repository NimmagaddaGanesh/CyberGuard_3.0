# Playbook PB-005: Agent Tool Abuse & Sandbox Revocation

## Purpose
Incident response procedure for mitigating autonomous agent rogue tool execution, unauthorized sandbox escapes, excessive permission exploitation, and boundary-crossing API calls.

## Detection Indicators
- Anomaly alerts from container/sandbox runtime (e.g., Falco, Sysdig, AWS GuardDuty) indicating unauthorized system calls (e.g., `execve`, `/bin/bash`, `curl`, raw socket bindings).
- Agent requesting tool calls outside its declared capability manifest (e.g., customer service agent attempting database DROP or outbound network requests).
- Tool execution rate spike or massive parameter mutation exceeding baseline quotas.
- Outbound egress connection attempts from isolated agent execution environments.

## Triage Steps
1. Identify the agent run ID, calling user session, invoked tool name, and exact tool invocation arguments.
2. Determine what prompt sequence or tool feedback triggered the unintended tool invocation.
3. Check what resources (filesystem, secrets, external APIs, databases) were touched or modified by the tool execution.
4. Assess whether the agent container/sandbox broke isolation boundaries.

## Containment Steps
1. **Immediate Tool Revocation:** Disable the affected tool in the agent tool registry or revoke its API credentials.
2. **Sandbox Termination:** Terminate the active agent worker container/pod immediately; do NOT allow the execution loop to continue.
3. Block outbound network traffic from the agent subnet to internal management planes and metadata endpoints (e.g., `169.254.169.254`).
4. Revert any state changes, files, or database rows modified during the abusive execution window.

## Remediation Steps
1. Apply the Principle of Least Privilege: Restrict tool execution parameters using strict Pydantic/JSON schemas with allowlists.
2. Enforce human-in-the-loop (HITL) approval gates for state-changing or high-risk tool actions (e.g., file deletion, external network calls, permission edits).
3. Harden the runtime sandbox with read-only root filesystems, dropped Linux capabilities (`CAP_DROP_ALL`), and gVisor/Firecracker microVM isolation.
4. Implement tool parameter canary tokens to detect parameter manipulation.

## Verification Steps
1. Execute canary execution tests with the hardened tool registry to verify unauthorized actions are blocked at schema level.
2. Verify that agent execution cannot reach unauthorized network interfaces or system binaries.
3. Confirm HITL approval mechanism blocks automated bypass attempts.

## Escalation Conditions
- Agent successfully performed state corruption on production databases, exfiltrated sensitive data, or breached host sandbox isolation -> Escalate to Infrastructure Security & Engineering Lead.
